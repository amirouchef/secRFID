Corriger la faille : authentification par secteur protégé

Fil rouge : vous corrigez ici la faille démontrée en séance 6, en ajoutant un second facteur de vérification au contrôle d'accès de la séance 4.

Cours

1. Pourquoi la liste blanche seule ne suffit pas

La séance 6 l'a démontré : un clone qui ne copie que l'UID (bloc 0) suffit à tromper un contrôle qui ne vérifie que l'UID. Pour résister à ce type d'attaque simple, il faut vérifier une information que le clone basique ne copie pas.

2. Authentification par secteur protégé

Idée : stocker une valeur secrète dans un secteur de données, protégé par une clé personnalisée (différente de la clé par défaut FFFFFFFFFFFF). Le programme n'accorde l'accès que si l'UID et le secret correspondent. Un clone qui n'a copié que le bloc 0 échouera à l'authentification de ce secteur.

3. Les limites qui restent

Cette défense reste contournable par un attaquant capable de cloner l'intégralité de la carte (toutes clés et données comprises) — ce que permettent certains outils plus avancés (Proxmark3, séance 10). C'est un principe de défense en profondeur : chaque couche supplémentaire élève le niveau d'effort requis, sans garantir une sécurité absolue. La solution réellement robuste (Mifare DESFire, AES) sera vue en séance 11.

Atelier

Objectif : ajouter un second facteur de vérification au système de la séance 4, et prouver qu'il résiste au clone de la séance 6.

Attention : changer la clé d'un secteur est une opération sensible — si vous perdez la nouvelle clé, le secteur devient définitivement inaccessible avec les outils de ce kit. Notez-la immédiatement sur votre livrable.

Étape 1 : choisir une nouvelle clé et un secret

Choisissez une clé A personnalisée de 6 octets (ex. {0x12,0x34,0x56,0xAB,0xCD,0xEF}) et une valeur secrète à écrire dans le secteur 1 (ex. un code à 4 chiffres).

Étape 2 : changer la clé A du secteur 1

Authentifiez-vous avec la clé par défaut, puis réécrivez le trailer (bloc 7) avec la nouvelle clé A, les mêmes bits d'accès, et la clé B inchangée :

byte nouveauTrailer[16] = {
  0x12, 0x34, 0x56, 0xAB, 0xCD, 0xEF,  // nouvelle clé A
  0xFF, 0x07, 0x80, 0x69,              // bits d'accès (inchangés)
  0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF   // clé B (inchangée)
};
rfid.MIFARE_Write(7, nouveauTrailer, 16); // bloc 7 = trailer du secteur 1
✓ Résultat attendu : écriture confirmée ; toute authentification ultérieure sur ce secteur doit désormais utiliser la nouvelle clé.

Étape 3 : écrire le secret

Authentifiez-vous cette fois avec la nouvelle clé, puis écrivez votre valeur secrète dans le bloc 4 (comme en séance 5, étape 4).

Étape 4 : modifier le contrôle d'accès

Dans le sketch de liste blanche de la séance 4, ajoutez une seconde vérification après le test d'UID :

MFRC522::MIFARE_Key cleSecrete;
byte cleSecreteOctets[6] = {0x12, 0x34, 0x56, 0xAB, 0xCD, 0xEF};
memcpy(cleSecrete.keyByte, cleSecreteOctets, 6);
byte secretAttendu[4] = {0x12, 0x34, 0x56, 0x78}; // votre valeur secrète

bool verifierSecret() {
  MFRC522::StatusCode status = rfid.PCD_Authenticate(
    MFRC522::PICC_CMD_MF_AUTH_KEY_A, 4, &cleSecrete, &(rfid.uid));
  if (status != MFRC522::STATUS_OK) return false; // mauvaise clé = pas le bon secteur

  byte buffer[18]; byte size = sizeof(buffer);
  status = rfid.MIFARE_Read(4, buffer, &size);
  if (status != MFRC522::STATUS_OK) return false;

  return memcmp(buffer, secretAttendu, 4) == 0;
}

// dans loop(), après le test d'UID :
bool autorise = uidConnu && verifierSecret();

Adaptez les noms de variables à votre code existant de la séance 4 ; l'essentiel est d'exiger les deux conditions (UID connu et secret valide) avant d'allumer la LED verte.

Étape 5 : tester badge légitime vs clone

  • Présentez le badge original : UID connu + authentification réussie avec la nouvelle clé + secret correct → accès autorisé.
  • Présentez le clone de la séance 6 : UID connu (copié), mais son secteur 1 n'a pas été modifié (clé toujours par défaut, pas de secret) → l'authentification avec la nouvelle clé échoue → accès refusé.
✓ Résultat attendu : la LED rouge s'allume pour le clone, verte pour l'original — la faille de la séance 6 est corrigée pour ce type d'attaque simple.

Dépannage

  • Authentification échoue même avec le badge légitime : vérifiez que la clé utilisée dans le code correspond exactement à celle écrite à l'étape 2.
  • Secteur devenu inaccessible : si la clé a été mal recopiée lors de l'écriture du trailer, le secteur peut être perdu — utilisez alors l'autre support (badge ou carte) pour continuer.

Débrief
